# 決まりの置き場所と流れ

## 決まりを層に分ける

今の形：

- `AGENTS.md` には、毎回要る大枠だけを書く。`CLAUDE.md` は `@` で取り込むだけ
- 1つのコマンドの中だけで要る手順は、手順スキル（`/dev-fix` など）に書く
- いくつかの作業で要る細かい決まりは、知識スキル（`user-invocable: false`）に書き、AIが作業に合わせて読む
- `.claude/rules/` は、`paths:` のファイルを触ったときに、どのスキルを読むかを伝えるだけにする。例外は、テンプレートのリポジトリだけで使う `template-notes.md`（`paths:` なしで、このフォルダを読ませる。下の「判断の理由は、このフォルダに書く」）

理由：2026年10月の作り直し（Issue #31〜#34、PR #35〜#38）の前は、決まりが多くの場所に積み重なり、大枠が埋もれて、決まり同士が食い違っていた。使う側では原因の分かりにくい不具合が出ていて、流れが重すぎることと、フックの誤作動が挙がった。AIには大枠だけを持たせ、細かいことは段階的に読み込ませる。

決まりを足すときは、足すだけでなく、まとめる・消すことも考える。足し続けると、作り直しの前と同じことが起きるため。

## 流れは2つ

今の形：`/dev-fix` と、`/dev-spec` →（`/dev-proto`）→ `/dev-impl` の2つ。機能の仕上げ（今の仕様・設計への反映、触って確かめる）は、別のコマンドにせず最後のタスクで行う。

作り直しのときに決めた。作り直しのきっかけの1つが、流れが重すぎることだった。

## Claude Code と GitHub Copilot で同じルールを使う

今の形：

- ルールは `AGENTS.md`、スキルは `.claude/skills/` に書き、両方が同じものを読む
- スキルでは `$ARGUMENTS` を使わず、「コマンドのあとに書かれた〜」と書く。両方で同じように読めるようにするため

条件：ルールやスキルを Copilot 用に分けなければならなくなったら、Copilot 用は別のリポジトリにする（人間が決めた）。2026-10-12 の時点では、分けずに済んでいる。

Copilot で効かない守りについては [guards.md](guards.md#copilot-で効かない守り)。

## 判断の理由は、このフォルダに書く

今の形：テンプレートの判断の理由は `docs/template-notes/` に書き、使う側では `scripts/link-template.sh` がテンプレートとつなぐときに消す。

理由：

- このリポジトリの `docs/design.md` などは、使う側のためのひな形なので、テンプレート自身の設計を書けない
- テンプレートのファイルに理由を書くと、使う側に写り、使う側のAIが毎回読むノイズになる
- PR の本文（コミットメッセージ）は使う側に写らない（「Use this template」では履歴が新しく始まる）が、今どの理由が効いているかをたどりにくい。そのため、今の理由はこのフォルダ、経緯は PR と分ける

消す場所を `link-template.sh` にした理由：`.template-version` を書くのと同じときに消せば、最初の PR（立ち上げの `/dev-proto` の PR、すでにあるリポジトリでは `.template-version` の PR）に一緒に入る。`setup-github.sh` ではなくこちらにしたのは、すでにあるリポジトリをつなぐときも通るため。

とらなかった案：

- 理由をテンプレートのファイルの中に、HTML コメントで書く：AIはコメントも読むので、使う側でもノイズになる
- 別のリポジトリや GitHub の Wiki に書く：テンプレートを直すAIが、同じリポジトリの中で読めない
