# 開発の土台を作る

技術を決め、テストを先に書いて開発を進められる土台を作る。Issue「開発を始められる」を、ほかの機能と同じ流れ（`/dev-spec` → `/dev-impl` × タスク数）で進める。
比べた候補などの経緯は仕様ファイルに残し、今の状態だけを `docs/overview.md`・`docs/design.md`・`CLAUDE.project.md` に移す。

## 仕様

- 使う場面と受け入れ条件は、開発する人（人間とAI）ができることで書く。技術の名前は書かない
  - 例：PR を出すと、テスト・Lint・型チェック・画面の画像を比べるテストが自動で走り、結果が PR に出る
  - 例：ファイルを編集すると、そのファイルだけが自動で整形される
- 画面はないので、プロトタイプは作らない

## 設計

- 技術は人間が決める。用途（言語・フレームワーク、データベース、テスト、デプロイ先）ごとに候補と良い点・悪い点を示して質問する
- 「設計」に、選んだものと理由に加えて、比べた候補と選ばなかった理由も書く（経緯は、ここにだけ残る）
- 構成（フォルダ、層の分け方、どの層に何を書くか）は、理由と前提も書く。最後のタスクで `docs/design.md` の「全体の構成」に移す
- まだ入れていないライブラリは、公式のドキュメントで使い方を確かめる

## 作るもの

- アプリのひな形。`create-next-app` などが既存のファイルで失敗する場合は、別のフォルダで作ってからこのリポジトリに移す
- テストが実行できること（ここが整わないと、テストを先に書けない）
- 本番のトークンファイル：立ち上げで仮置きした `docs/tokens.css` を本番の置き場所へ移し（`docs/tokens.css` は消す。同じ値を2か所に置かないため）、場所を `docs/ui.md` の「トークン」に書く。これ以降、トークンは本番のファイルだけを直す
  - `docs/tokens.css` がなければ、止まって人間に伝える（プロトタイプのフォルダは読まない）
- 本番の画面を撮る仕組み（screenshots スキル）
  - 複数のタスクを並べて進める（worktree などでフォルダを分ける）なら、撮るときに立ち上げるサーバーのポートを、フォルダごとに変えられるようにする
- CI（GitHub Actions）：PR ごとに、テスト・Lint・型チェック・画像を比べるテストを走らせる
  - `pull_request` で動かす
  - 画像を比べるテストのジョブは、`container:` に Playwright 公式の Docker イメージを指定する。タグのバージョンは、入れた Playwright と同じにする
  - 失敗したら、Playwright のレポート（基準・今回・差分の画像）をアーティファクトとして残す
  - CI では基準の画像を更新しない。撮り直しは手元の同じイメージで行い、PR に入れる
  - CI が動いたら、マージの前に PR で CI の結果を確かめるよう人間に伝える。非公開のリポジトリで GitHub Free だと、CI が失敗していてもマージできてしまうため。main のブランチ保護を設定できていたら、CI のジョブを必須にする（`required_status_checks`）ことも伝える
- ファイルを編集したあとに、フォーマットと Lint を走らせるフック（`.claude/settings.json`）
  - `PostToolUse` で、matcher は `Edit|Write`。入力の `tool_input.file_path` のファイルだけにかける。対象でない種類のファイル（`.md`、画像など）では何もしない
  - 失敗しても作業は止めない。Lint のエラーは、テストと CI で見る
  - `command` と `args` で書き、shell を通さずに起動する。Windows では `npx` などの `.cmd` を直接起動できないので、`node` でスクリプトを起動する。Windows で、実際にファイルを編集して動くことを確かめる
- `.claude/rules/testing.md` の `paths:` を、決めた技術のテストのファイルの置き場所に合わせる
- `README.md` を、GitHub で見た人向けに埋める

CI とフックのひな形は、テンプレートに置いていない。`.github/workflows/` に置くと、立ち上げの前から push のたびに動いて失敗するため。また、コマンドや Docker イメージのバージョンは、技術を決めるまで決まらないため。

## タスクの順番

1. ひな形と、テストが実行できること。同じタスクPRで、`docs/overview.md` の「技術」（選んだものと理由を1行）と、`CLAUDE.project.md` の「技術」「よく使うコマンド」を書く。`test-runner` は、`CLAUDE.project.md` のコマンドがないと動かないため
2. 本番のトークンファイル
3. 本番の画面を撮る仕組み。撮り直すコマンドと比べるテストのコマンドを、`CLAUDE.project.md` の「よく使うコマンド」に足す
4. CI（撮る仕組みのあと。撮るのと同じイメージで比べるため）
5. 編集したあとのフックと、`.claude/rules/testing.md` の `paths:`
6. `README.md`

- 撮る仕組みができるまでは、`test-runner` が画像を比べるテストを「コマンドが未設定」と返す。失敗として扱わない
- ひな形やライブラリの動きはテストを書かない（testing スキル）。確かめ方は、多くが「触って確かめる」か「コードを見て確かめる」になる

## 仕上げ（最後のタスク）

- `docs/specs/` に書く動きはない
- `docs/design.md` の「全体の構成」に、構成と理由・前提を書く。比べた候補は書かない
- `docs/overview.md` の「技術」と、`CLAUDE.project.md` の「技術」「よく使うコマンド」が、今の状態と合っているか確かめる
