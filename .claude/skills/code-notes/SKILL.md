# 理由と前提の残し方

後から変えるときに「変えてよいか」を判断できるよう、判断の理由と前提（なぜそのやり方にしたか、何が崩れたら見直すか）を残す。
**1つの理由は1か所だけに書く**。置き場所は、影響する範囲で決める。

| 影響する範囲 | 置き場所 | 書く時 |
| --- | --- | --- |
| そのコードだけ | コードのコメント | 実装するとき |
| 複数の場所（整合性に関わる） | `docs/design.md` | 決まりができたタスクPR、または機能の最後のタスクPR |
| 見た目（色や部品の使い分け） | `docs/ui.md` | 同上 |

- 迷ったら「この前提が崩れたら、直すのは1か所だけか？」。1か所ならコメント、複数なら `docs/design.md`
- `docs/design.md` の決まりに従っているだけのコードには、理由を書き写さない。普通とは違って見えるところだけ、`docs/design.md の「〇〇」` と見出しを1行で示してよい
- `docs/changes/` は、比べた選択肢などの経緯の記録。理由の置き場所にはしない（AIは過去の `docs/changes/` を読まない）
- `docs/specs/` には動きだけを書き、理由は書かない

## `docs/design.md` に書くもの

- 全体の構成（フォルダ構成、層の分け方、どの層に何を書くか）
- データの持ち方
- どこでも守る決まり。ライブラリの使い方の注意で、コードの書き方を縛るものもここ（例：このデータベースの接続方法ではトランザクションが使えないので、1回の操作は1つのSQLにする）
- 「今どう作られているか」を現在形で、理由と前提つきで書く。経緯は書かない
- 1つの決まりは、次の形で書く

  ```
  ### データベースの1回の操作は1つのSQLにする
  - 理由：この接続方法ではトランザクションが使えない
  - 前提（崩れたら見直す）：接続方法を変えたら、この決まりは要らなくなる
  - 当てはまる場所：src/db/ のすべての関数
  ```

- 長くなったら `docs/design/` に分ける

## コメントに書くもの・書かないもの

- 書くもの
  - 普通とは違うやり方を選んだ理由（例：データベースではなくアプリで並べ替える）
  - 外すと壊れる前提、崩れたら見直すべき前提（例：一覧は多くても数十件まで）
  - 試してだめだったやり方
  - 実装中に決めた細かいこと（仕様ファイルの「設計」に書かれていない判断）
- 書かないもの
  - コードを読めばわかること（何をしているかの言い換え）
  - 複数の場所に関わる決まりと、その理由（`docs/design.md` に書く）

## ライブラリの資料

新しいライブラリを入れたタスクPRで、`docs/libraries/<ライブラリ名>.md` の下書きを書く。人間がコードを読むための資料。

- 冒頭に、書いた時点のバージョンを書く
- 簡単な説明と、このプロジェクトで使っている部分。公式ドキュメントの写しにはせず、公式へのリンクを書く
- 言語そのものの知識、ドメインの知識、アプリに特有の決まりは書かない（`docs/overview.md`・`docs/specs/`・`docs/design.md` に書く）
- AIは実装のときに読まない（古くなった説明を頼りに書かないため。使い方はインストール済みの型定義やドキュメントで確かめる）。AIに守らせたい注意は `docs/design.md` に書く
