Issue #<番号> を、1つの PR で直す。`<番号>` は、コマンドのあとに書かれた Issue 番号。

1. `gh issue view <番号>` で Issue を読み、関係する `docs/specs/` と、変わりそうなコードを読む
2. 下の「機能の流れにするもの」に当たるか確かめる。当たれば、どれに当たるかを伝え、`/dev-spec <番号>` を使うよう伝えて止まる。迷うときも止まって人間に聞く
3. 「どうなるべきか」が Issue に書かれていない、または `docs/specs/` と食い違う場合は、**直す前に** 人間に伝えて決めてもらう
4. main を最新にして、`<番号>-<英語の短い名前>` ブランチを作る
5. 動きが変わるなら、**バグを再現するテスト、または新しい動きのテストを先に書き、実行して失敗することを確かめる**（実行はサブエージェント `test-runner` に、書いたテストのファイルを渡して頼む）。コミットする
   - testing スキルに従う。文言・誤字や、動きを変えない整理など、「テストを書かないもの」に当たれば新しいテストは書かない
6. 直す。テストが通ったらコミットする。Issue と関係ない所は変えない
   - 原因が、どこにも書かれていなかった前提だった場合は、その前提を書く（code-notes スキル）
   - 途中で「機能の流れにするもの」に当たるとわかったら、**止まって伝える**
7. 画面を変えたなら、変えた画面だけを撮り直してコミットする（screenshots スキル）
8. サブエージェント `test-runner` に「全部」を渡し、テスト・Lint・型チェック・画像を比べるテストがすべて通ることを確かめる。失敗したら直して、もう一度頼む
9. 動きや文言が変わったなら、`docs/specs/` も同じブランチで直す（仕様のほうが間違っていたと決まった場合も）
10. 動きが変わったなら、サブエージェント `pr-check` に Issue の本文（「どうなるべきか」と、人間と決めたこと）を渡し、差分を確かめさせる。ずれは直し、直さないものは理由を PR の「レビューで見てほしいところ」に書く
11. PR を出す
    - タイトル：何をしたかの日本語1文
    - 本文：`.github/pull_request_template.md` に沿い、**`Closes #<番号>`**。画面を撮り直したなら、撮り直した画像の一覧を「やったこと」に書く
12. CI の結果を `gh pr checks --watch --fail-fast` で、終わるまで待って確かめる（PR を出した直後は、まだ動いているため）。失敗していたら直してから次へ進む
    - `no checks reported` と出たら（exit 1 で終わる）、失敗として扱わない。`.github/workflows/` がなければ、CI はまだないので確かめずに進み、最後に「CI がまだないので確かめていない」と伝える。あれば、チェックがまだ登録されていないので、少し待ってからもう一度確かめる
13. PR の URL と、何をしたか（バグなら原因）を短く伝える

**マージはしない。**

## 機能の流れにするもの

変更が小さくても、次に当たれば仕様ファイルを作る（`/dev-spec`）。変更の大きさではなく、うまくいかなかったときの影響で決める。

- 新しい画面や機能。受け入れ条件が3つ以上になりそうなもの
- データの形や保存の仕方が変わる（今あるデータの移し替えが要るもの）
- ログイン・権限・お金・個人情報に関わる
- 削除など、取り消せない操作に関わる
- 複数の画面で使う部品や、トークンの値を変える
- 外部のサービスとのつなぎ方を変える
- `docs/design.md` の決まりを変える・足す
