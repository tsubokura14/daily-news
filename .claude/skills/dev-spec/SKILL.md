引数（コマンドのあとに書かれたもの）の機能の、仕様・設計・タスクを書く。**コードはまだ書かない。**

- 引数が Issue 番号（以下 `<番号>`）なら、「A. 仕様」から始める
- 引数が仕様ファイルなら、`/dev-proto` のあとの続き。仕様ファイルがある `<Issue番号>-spec` ブランチ（`git branch --list "*-spec"` で探す。複数あれば、`git show <ブランチ>:<仕様ファイル>` で、そのファイルがあるブランチを選ぶ）に切り替え、「B. 設計とタスク」から始める

## A. 仕様

1. `gh issue view <番号>` で Issue を読む。`docs/ui.md` と、関係しそうな `docs/specs/`（`docs/specs/screens/` を含む）を読む
   - Issue に `docs/agreed-screens/` の画像が書かれていたら、その画面は立ち上げのプロトタイプで合意済み。画像を読む
2. main を最新にして `<番号>-spec` ブランチを作る。`docs/changes/_template.md` をコピーして `docs/changes/<今日の日付 YYYY-MM-DD>-<何をするかの英語名>.md` を作り、コミットする（下書きを、ほかの作業の PR に混ぜないため）
   - 名前は機能名ではなく「何をするか」（例：`add-due-date`）。同じ名前のファイルがあれば変える
3. Issue とこれまでの会話からわかる範囲で「なぜ」「影響する今の仕様」「使う場面」「受け入れ条件」「画面」「やらないこと」を下書きする
   - 使う場面：具体的な人・データ・操作の順で、1〜3つ書く（例：期限が3日後のタスクを持つ人が、一覧を開くと〜と表示される）
   - 画面：画面が変わるなら、変わる画面と、0件・大量・読み込み中・エラー・権限なしのうちその画面で起こる状態ごとの表示を書く
   - 合意済みの画面は、文言・見た目・状態ごとの表示を一から決めない。`docs/agreed-screens/` の画像と Issue の本文から書き起こし、「画面」の表から画像を参照する。画像と Issue から読み取れないことだけを「決まっていないこと」にする
   - わからないところは推測で埋めず、「決まっていないこと」に質問として書く
   - 受け入れ条件に技術の話を書かない（技術は「設計」に書く）
4. 下書きを元に、自分の理解を数行で言い換えて人間に確かめる（「〜という理解で合っていますか」）。違っていたら直す
5. 次の観点で、問題点を **質問の形で** 挙げる
   - 受け入れ条件の抜け（エラーのとき、データが空のとき、ログインしていないとき、境界の値）
   - あいまいな表現、画面の文言が決まっていないところ
   - `docs/specs/` や `docs/overview.md` の用語との食い違い
   - 1つの機能として大きすぎないか（大きすぎるなら分け方の案）
   - `docs/overview.md` の「やらないこと」に触れていないか
6. 人間の答えを仕様ファイルに反映し、コミットする。「決まっていないこと」には答えも残す（`- [x] 質問 → 答え`）
7. 決まっていないことが0になったら、プロトタイプが要るかを決める
   - 合意済みの画面があるか、下の表で「作る」に当たるなら、ここで終わる。会話を区切り、新しい会話で打つ1行 `/dev-proto <仕様ファイルのパス>` を伝える（合意済みの画面は、プロトタイプと見比べて撮り直すため。プロトタイプを読む会話と設計する会話を分けるため）
   - それ以外は、同じ会話で「B. 設計とタスク」に進む

| プロトタイプを作る | 作らない |
| --- | --- |
| 新しい画面 | 文言だけの変更 |
| 画面の流れやレイアウトが変わる | 今ある見せ方の範囲で、項目を足す・減らす |
| `docs/ui.md` にない見せ方や部品が要る | 内部処理だけの変更 |
| 操作の手触りを言葉で決めにくい | バグ修正 |

## B. 設計とタスク

1. 仕様ファイルと同じ名前のフォルダのスクリーンショット、`docs/ui.md`、関係する `docs/specs/`、既存のコードを読む
2. 「決まっていないこと」に未回答（`- [ ]`）が残っていたら、先に進まず人間に伝えて止まる
3. 使うライブラリは、インストールされているバージョンの型定義やドキュメントで使い方を確かめる（まだ入れていないものは、公式のドキュメントで）
4. やり方が複数ありうる点は、**書く前に** 選択肢と良い点・悪い点を示して質問する。人間が選んだら、比べた選択肢と選ばなかった理由も「設計」に残す（経緯の置き場所はここだけ）
5. 「設計」に書く：変えるファイル、データの変更、そのやり方を選んだ理由
   - 理由と前提には、機能を仕上げたあとに残す場所（コメントか `docs/design.md`）も書く（code-notes スキル）
   - データの形は、受け入れ条件と使う場面から決める。スクリーンショットに写っている項目名や並びから決めない
   - 画面は、今ある本番の部品で作る。`docs/ui.md` にない部品や見せ方が要るなら、書く前に人間に伝えて決めてもらう
   - `docs/design.md` と食い違う設計になるなら、書く前に人間に伝えて決めてもらう
6. 「確かめ方」に、受け入れ条件ごとに「テスト」「触って確かめる」「コードを見て確かめる」のどれかを書く（testing スキル）。すべての受け入れ条件に確かめ方があること
7. 「タスク」に分ける
   - 1タスク = 1ブランチ = 1PR。人間が1回でレビューできる大きさ
   - 「〜ができたら完了」と1文で言える
   - データの変更と画面は別のタスクにする
   - 画面のタスクには、合わせるスクリーンショットのファイル名を書く
   - どのタスクを取り込んでも、アプリが壊れない順番にする（例：まだない画面へのリンクを、その画面より先のタスクで作らない）
8. 人間のレビューを待つ。承認されたらコミットし、PR を出す。ブランチには、仕様ファイルと、同じ名前のスクリーンショットのフォルダだけを入れる
   - タイトル：`<機能の名前>の仕様・設計・タスク`
   - 本文：`.github/pull_request_template.md` に沿い、`Refs #Issue番号`
9. PR の URL と、マージしたあとに打つ1行 `/dev-impl <仕様ファイルのパス> <最初のタスク>` を伝える。**マージはしない**
