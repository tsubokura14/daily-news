画面のプロトタイプを作る。決まりは [prototype.md](prototype.md) に従う。**本番のコードは書かない。**

引数（コマンドのあとに書かれたもの）が空なら「立ち上げ（S3）」、仕様ファイルなら「変更」として進める。

## 準備

1. [prototype.md](prototype.md)、`docs/ui.md` を読む
2. プロトタイプのフォルダが作業ディレクトリに入っているか確かめる。入っていなければ、人間に場所を聞き、フォルダを作って `/add-dir <フォルダ>` で加えてもらうよう頼んで止まる
   - このリポジトリの外で、本番の作業の作業ディレクトリに入らない場所にする
   - 加えるのはこの会話だけ。設定には保存しない
3. フォルダが空なら、次を作り、`git init` してコミットする
   - `index.html`：画面と状態の一覧。人間が最初に開くページ
   - `pages/<画面の英語名>.html`：1画面1ファイル。状態は `?state=<状態>` で切り替える。表示用のデータは、ページに決まった値で書く
   - `tokens.css`：トークン。Tailwind の CLI でビルドし、ビルド結果の CSS もコミットする（ファイルをブラウザで開くだけで見られるように）
   - スクリーンショットを撮るスクリプト：Playwright で、画面と状態の組み合わせごとに `<画面>-<状態>.png` を保存する。保存先は引数で受け取る
4. 本番のトークンファイル（場所は `docs/ui.md` の「トークン」）があれば、`tokens.css` に上書きでコピーする。プロトタイプから本番へはコピーしない

## 立ち上げ（引数が空）

1. 雰囲気の案を作る：`docs/overview.md` の主な機能から代表の画面を1つ選び、雰囲気の違う2〜3案を作る。案ごとにトークンを分ける
2. 人間に1つ選んでもらう。選んだ案のトークンを `tokens.css` にし、ほかの案は消す
3. 選んだ案から `docs/ui.md` を書く。値は書かず、使い分けと理由を書く
4. 主な機能の画面と、画面のつながりを作る
   - 状態は、0件・大量・読み込み中・エラー・権限なしのうち、その画面で起こるものをすべて作る
   - `docs/overview.md` にない機能・画面を足さない。足したほうがよさそうなら質問する
5. 人間に `index.html` から触ってもらい、直しを聞く。合意するまで繰り返す
   - 決まった機能・用語・やらないことは、その場で `docs/overview.md` に書く
   - 決まった見た目の決まりは、その場で `docs/ui.md` に書く
6. 合意したら、作ったすべての画面を状態ごとに撮り、`docs/agreed-screens/<画面>-<状態>.png` に保存する
   - 画面ごとの文言・アイコン・状態ごとの表示は、ここでしかプロトタイプの外に出ない。`/dev-spec` はこの画像から仕様を書き起こす
7. 主な機能を Issue に分ける案を出す（タイトルは「〇〇できる」の1文）。人間が承認したら Issue を作る
   - 本文に、関係する画面の名前、合意した画面のつながり（どの画面のどの操作で、どこへ行くか）、関係する `docs/agreed-screens/` の画像のパスを書く。画像に写らない動き（開閉、確認の出方、操作のあとどうなるか）も書く。プロトタイプは本番の作業で読めないので、`/dev-spec` の手がかりを Issue に残す
   - 同じときに、立ち上げの S4 の Issue「開発を始められる」も作る。本文は「技術を決め、テストを先に書いて開発を進められる土台を作る。foundation スキルに沿う。」
8. 次の会話に要るものが、リポジトリと Issue に入っているか見直す。次の会話ではプロトタイプを読めないため
   - この会話で決まった機能・用語・やらないことが `docs/overview.md` に、見た目の決まりが `docs/ui.md` に入っているか
   - 作った画面と状態のすべてに、`docs/agreed-screens/` の画像があるか
   - 各 Issue に、関係する画面・画面のつながり・画像のパス・画像に写らない動きが書かれているか
   - 抜けていたら書き足し、書き足したものを人間に伝える
9. プロトタイプのフォルダでコミットする。このリポジトリでは、main から `ui-foundation` ブランチを作り、`docs/ui.md`・`docs/overview.md`・`docs/agreed-screens/` と、プロトタイプの `tokens.css` を `docs/tokens.css` にコピーしたもの、立ち上げの S2 でできた `.template-version` と、そのとき消したテンプレートだけで使うファイル（まだコミットされていなければ）をコミットして PR を出す
   - `docs/tokens.css` は、立ち上げの S4 で本番のトークンファイルを作るときの元になる仮置き。本番の置き場所は技術を決めるまで決まらないため
   - タイトル：`画面の雰囲気と主な機能を決める`
   - 本文：`.github/pull_request_template.md` に沿う。対応する Issue はないので、`Refs` の行は消す
10. 次を伝えて終わる
   - PR の URL。**PR をマージしてから** 次へ進む（`/dev-spec` は main からブランチを作るので、マージ前だと `docs/ui.md` などが入っていない）
   - 会話を区切り、新しい会話で打つ1行：`/dev-spec <「開発を始められる」の Issue 番号>`（番号を入れて、そのまま貼れる形で）

## 変更（引数が仕様ファイル）

1. 仕様ファイルがある `<Issue番号>-spec` ブランチ（`/dev-spec` で作ったもの。`git branch --list "*-spec"` で探す。複数あれば、`git show <ブランチ>:<仕様ファイル>` で、そのファイルがあるブランチを選ぶ）に切り替える。引数の仕様ファイルと、関係する `docs/specs/`（`docs/specs/screens/` のスクリーンショットを含む）、変わる画面の `docs/agreed-screens/` の画像を読む。「決まっていないこと」に未回答（`- [ ]`）が残っていたら、人間に伝えて止まる
2. 変わる画面ごとに、プロトタイプのどこから始めるかを決める
   - **合意済みの画面**（`docs/agreed-screens/` に画像がある。立ち上げで合意し、まだ本番にない）：プロトタイプを作り直さない。本番に合わせることもしない。プロトタイプと仕様ファイルを見比べ、食い違い（文言、状態ごとの表示、仕様にない要素、プロトタイプにない状態）を一覧にして、どちらに合わせるかを人間に選んでもらう。答えを先に仕様ファイルに書き、手順3では、選んだ答えに合わせて直すところだけを直す。食い違いがなければ、手順3・4を飛ばして手順5で撮る
   - **本番にある画面**：プロトタイプが `docs/specs/screens/` と違っていたら（本番だけが直されたなど）、先にプロトタイプを今の本番に合わせる
   - **プロトタイプにない画面**：スクリーンショットと `docs/specs/` から作る
3. 仕様ファイルの「受け入れ条件」と「画面」に沿って、変わる画面を作る。「画面」に書いた状態はすべて作る
   - 仕様にない要素を足さない。足したほうがよさそうなら質問する
4. 人間に `index.html` から触ってもらい、直しを聞く。合意するまで繰り返す
   - 決まったことは、その場で仕様ファイルに書き戻す（「受け入れ条件」「画面」「決まっていないこと」）。プロトタイプにしか残っていない決めごとを作らない
   - `docs/ui.md` にない見た目の決まりができたら、仕様ファイルの「画面」に書く（`docs/ui.md` へは機能の最後のタスクで移す）
5. 合意したら、変わった画面の状態ごとにスクリーンショットを撮る
   - 保存先：`docs/changes/<仕様ファイルと同じ名前>/<画面>-<状態>.png`
   - 仕様ファイルの「画面」から、画像を参照する
6. 次の会話に要るものが、仕様ファイルに入っているか見直す。次の会話ではプロトタイプを読めないため
   - この会話で決まったこと（直しの中で決めた動き・文言・見た目を含む）が、「受け入れ条件」「画面」「決まっていないこと」に入っているか
   - 「画面」に書いた状態のすべてに、スクリーンショットがあり、参照が切れていないか
   - 「決まっていないこと」に未回答（`- [ ]`）が残っていないか
   - 抜けていたら書き足し、書き足したものを人間に伝える
7. プロトタイプのフォルダでコミットする。このリポジトリでは、仕様ファイルとスクリーンショットを `<Issue番号>-spec` ブランチにコミットする（PR は `/dev-spec` の続きで出す）
8. 会話を区切り、新しい会話で打つ1行を伝える：`/dev-spec <仕様ファイルのパス>`（パスを入れて、そのまま貼れる形で）。続きの設計とタスク分けから再開する。本番の作業に、プロトタイプの中身を持ち込まないため

**本番のコードは書かない。マージはしない。**
