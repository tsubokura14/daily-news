# 機能を仕上げる（最後のタスク）

最後のタスクのブランチで、PR を出す前に行う。仕上げのための PR は別に出さない。

## PR を出す前

1. 受け入れ条件ごとに、確かめ方と結果を表にする
   - 「テスト」：対応するテストの場所と、実行して通るか（実行はサブエージェント `test-runner` に頼む）
   - 「触って確かめる」：人間が操作する手順
   - 「コードを見て確かめる」：見る場所（ファイルと行）と、そこに書かれている値
2. 人間に、表の「触って確かめる」「コードを見て確かめる」ものを、このブランチで確かめてもらう。問題があれば、このタスクで直すか、新しい Issue にするかを人間に聞いて止まる
3. 変わった動きを `docs/specs/` に反映する
   - 「今どう動くか」だけを現在形で書く。なぜ変えたかは書かない
   - 機能のまとまりごとのファイルに書く。合うファイルがなければ `docs/specs/_template.md` から作る
   - 画面が変わったなら、画面の表（状態と表示）を書き、`docs/specs/screens/` の画像を参照する。表にある状態の画像がなければ、撮る（screenshots スキル）
   - `docs/specs/screens/` に入った画面と状態の画像が `docs/agreed-screens/` にあれば、消す（本番の画像に引き継がれたため）
4. 仕様ファイルの「設計」と「画面」を、残す場所（コメント、`docs/design.md`、`docs/ui.md`）に反映する（code-notes スキル）。前のタスクPRで書き足し済みなら、食い違いと抜けがないかだけ確かめる
   - 技術を足した・変えたなら、`docs/overview.md` の「技術」と、`CLAUDE.project.md` の「技術」「よく使うコマンド」が今の状態と合っているか確かめる
5. コミットする。PR の本文は **`Closes #Issue番号`** にする

## PR を出したあと

最後に伝えることに、次を足す。

- 作業中に出てきた新しい要望やバグ：Issue にする候補の一覧（作るのは人間の承認後）
- この機能で、AIへの指示がうまくいかなかったこと・同じ注意を繰り返したこと：`CLAUDE.project.md` の「うまくいかなかったことから追加したルール」に足すルールの案。原因がテンプレートのもの（`docs/template-files.md`）にあるなら、そのファイルを直す案にする
- この機能で出た確認（push や PR 作成などの承認）について、断ったもの・毎回そのまま承認したもの・確認なしで実行されて困ったものがあったかを聞く。あれば、permissions スキルに沿って、権限の変え方の案を出す
- `.template-version` があれば、`git fetch template main` を実行する。`template/main` が `.template-version` の `commit` より新しければ、`/template-sync` で取り込めると伝える
