# 本番の画面を撮る

本番の画面は、AIが Playwright で撮る。人間は撮らない。撮った画像は、次の2つに使う。

- `docs/specs/screens/` の「今の画面」。本番から撮るので、いつも本番と同じになる
- 画像を比べるテストの基準。画面を変えるつもりのない変更で見た目が変わったら、テストが失敗する

## 撮り直すとき

| 場面 | すること |
| --- | --- |
| 画面のタスク（`/dev-impl`） | **タスクに書かれた画面だけ** を、撮る状態を足して撮り直す。画像を開いて、合意したスクリーンショットと見比べる。違いは直し、直せないものは PR に書く |
| 小さな変更・バグ修正（`/dev-fix`） | 変えた画面だけを撮り直す |
| 画面を変えるつもりのない変更 | 撮り直さない |

- 上で撮り直す画面以外で、比べるテストが失敗したら、**撮り直さずに止まり**、どの画面がどう変わったかを伝える。意図しない変化まで撮り直して、テストを通してしまわないため
- 撮り直した画像は、その変更と同じ PR に入れ、一覧を PR 本文に書く
- 機能の途中では、`docs/specs/screens/` の画像が、`docs/specs/` の文章より先に新しくなる。文章は機能の最後のタスクPRで追いつく。比べるテストの基準を2か所に分けないため、画像はタスクPRで更新する
- プロトタイプと本番は作りが違うので、細かい差は残る。見比べるのは、合意したレイアウト・色・文言・状態ごとの表示が合っているか

## 仕組み（立ち上げで作る）

- 画面と状態の組み合わせごとに `<画面>-<状態>.png` を撮る。撮る状態は、`docs/specs/` の画面の表にある状態
- 状態（0件、エラー、読み込み中など）は、テスト用のデータで作る。作り方は技術で決まるので、`docs/design.md` に書く
  - 画面がブラウザ側でデータを取ってくる作り：通信の返事を差し替える（Playwright の `page.route`）
  - サーバー側で画面を組み立てる作り：テスト用のデータベースに、決まったデータを入れる
- ログインが要る画面は、テスト用のユーザーでログインして撮る
- 撮るたびに変わるもの（今日の日付、アニメーション）は止める。日時は固定する
- 撮る環境は、**Playwright 公式の Docker イメージ**（入れた Playwright と同じバージョン）にする。手元で撮り直すときも、CI で比べるときも、同じイメージで動かす。OS が違うと文字の描き方が変わり、画像が一致しないため。手元では Docker Desktop が要る
- 基準の画像の場所を `docs/specs/screens/` にし、名前に OS 名を入れない（`snapshotPathTemplate` など。設定の名前は、入れたバージョンのドキュメントで確かめる）
- 撮り直すコマンドと、比べるテストのコマンドを、`CLAUDE.project.md` の「よく使うコマンド」に書く
